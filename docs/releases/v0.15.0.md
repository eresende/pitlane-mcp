## pitlane-mcp v0.15.0 — documentation discovery, scoped calls for Python/TypeScript, and friendlier project-path errors

This release widens what navigation can see beyond source code: Markdown headings and JSON/YAML/TOML configuration keys become first-class lookup targets alongside symbols; call edges are now extracted from the syntax trees of Python and TypeScript and resolved with scope against lexical targets and imports instead of dropped as unresolvable; and every tool accepts either `path` or `project`, so a missing project parameter returns an actionable error naming both accepted spellings instead of a raw deserialization failure. Two features and three fixes landed; the test suite grew from 670 to 692 tests.

### Documentation and configuration discovery (#103)

`locate_code` now resolves Markdown headings (`intent: "docs"`, `kind: "section"`) and JSON/YAML/TOML keys (`intent: "config"`, `kind: "config_key"`), with document language filters `markdown`, `json`, `yaml`, and `toml`. Each result carries a `read_target` that feeds straight into `read_code_unit`: repeated headings and array/table keys remain separate locations, Markdown sections extend to the next heading of equal or higher level, and config ranges include the key's value. Passing a document file path without line bounds returns a bounded outline of sections/keys; explicit line reads keep the normal retrieval and freshness behavior (at most 500 lines per read). `search_content` covers Markdown, JSON, YAML, and TOML text as well, with the same language filters.

Documents are parsed from current files on demand — they are never embedded or stored as code symbols — so new and edited documents are visible without re-indexing, heading/key matching is lexical rather than semantic, and document results create no call-graph edges. When a Markdown section backticks a symbol name or a config key exactly matches one, up to three `related_source` candidates link the two with explicit lexical evidence (`resolved: false`).

### Python and TypeScript calls resolve in scope (#105)

Call sites are extracted from the syntax trees of both languages (TSX grammar selected by file extension) and resolved against same-file lexical targets plus explicit imports, including aliases and namespace imports. Receiver type annotations and straightforward constructor assignments distinguish same-name methods on different receivers. Resolved and ambiguous graph edges carry a `resolution` field; candidates that cannot be disambiguated stay `references` rather than becoming fabricated call edges, so the navigation graph only gains confidence it can defend. Advanced `get_symbol(include_references=true)` responses additionally include `unresolved_calls`, with per-call-site evidence and machine-readable reasons such as `dynamic_receiver` or `no_visible_target`.

### One project path for every tool (#109, #111, #117)

Every request type now accepts both `path` and `project` for the project root via serde aliases. Canonical schema names are unchanged — no breaking change: `ensure_project_ready`/`index_project` keep canonical `path`, all other tools keep canonical `project`. `get_project_outline` is the exception by design; its own `path` field filters subdirectories, so only `project` names the project root there.

Omitting the required parameter entirely used to surface as a raw serde failure (`missing field 'path' at line 1 column 2`). Tools now return an actionable error instead — "Missing required project-path parameter. Use either `project` or `path`. Example: `{ \"project\": \"/path/to/project\" }`" (canonical-only for `get_project_outline`) — with a data-driven regression guard asserting that every project-requiring tool emits the friendly form, and per-tool wrapper boilerplate replaced by a generic `Friendly<T>` plus parameter table while leaving each tool's published input schema untouched. Both behaviors are documented in `docs/tools.md`.

### Validation

- 692 Rust tests pass; formatting and Clippy checks pass on Linux x86_64, Linux ARM64, macOS Apple Silicon, macOS x86_64, and Windows x86_64.
- Alias acceptance verified end-to-end over the MCP protocol: both spellings round-trip on every request type, with a data-driven regression guard asserting that each project-requiring tool emits the friendly missing-parameter error (canonical-only for `get_project_outline`).
- Verified live against the v0.15.0 binary over stdio MCP: omitting the parameter on `locate_code` returns `isError=true` with "Missing required project-path parameter. Use either 'project' or 'path'. Example...", and a nonexistent path passed via either spelling yields an actionable structured error instead of deserialization noise.
