## pitlane-mcp v0.12.0 — external embedding endpoints and MCP protocol 2026-07-28

This release adds support for external OpenAI-compatible embedding endpoints, upgrades the MCP protocol layer to rmcp 3.1, and introduces proactive rate limiting for hosted embedding APIs.

Pitlane semantic search no longer requires a local Ollama instance. Any reachable OpenAI-compatible embedding endpoint — including Jina, OpenAI, Azure, or company-internal gateways — can now serve as the vector backend, with credential management, retry logic, and concurrency controls built in.

### External embedding endpoints

`PITLANE_EMBED_URL` can now target any reachable OpenAI-compatible endpoint. The endpoint must accept `model` and `input` fields and return `data[i].embedding`. Authentication, arbitrary request headers, concurrency, and retry behavior are all configurable through environment variables.

Credential header values are deliberately excluded from embedding cache identity, so rotating API keys does not trigger a vector rebuild. Non-secret routing headers, such as tenant identifiers, are included in cache identity.

HTTPS requests trust both public WebPKI roots and certificates installed in the operating system's native trust store, including company-internal CAs.

New environment variables:

- `PITLANE_EMBED_API_KEY` adds an `Authorization: Bearer ...` header
- `PITLANE_EMBED_HEADERS` adds arbitrary request headers from a JSON object of string values
- `PITLANE_EMBED_MAX_CONCURRENCY` limits concurrent endpoint requests (default `16`)
- `PITLANE_EMBED_MAX_RETRIES` retries `429` and transient `5xx` responses (default `3`)
- `PITLANE_EMBED_RETRY_BASE_MS` sets exponential backoff when `Retry-After` is absent (default `500`)

### Proactive rate limiting

`PITLANE_EMBED_REQUEST_DELAY_MS` adds a configurable inter-request delay to stay within external API rate limits (e.g. 100 RPM on the Jina free tier). Each batch request sleeps for the configured delay before sending, preventing 429s proactively instead of relying solely on retry-after backoff.

Defaults to `0` (disabled) for backward compatibility with local Ollama and other unlimited endpoints.

### rmcp 3.1 protocol upgrade

The MCP framework dependency moves from rmcp 2.2 to 3.1.2. The migration adapts to rmcp's split of the former unitary `Meta` type into `MetaObject` (response-side) and `RequestMetaObject` (request-side).

The tier-aware `tools/list` handler now reads the negotiated protocol version from `RequestContext`. Clients negotiating MCP `2026-07-28` receive the required `resultType`, `ttlMs`, and `cacheScope` fields, while legacy clients retain their prior wire shape. rmcp's dispatcher removes those fields for older peers automatically.

Two new stdio integration tests exercise the complete initialize and `tools/list` exchange for both `2025-11-25` and `2026-07-28` protocol versions.

### Other changes

- Added comprehensive RMCP protocol test suite for wire-level regression coverage.
- Updated anyhow, clap, futures, globset, libc, serde, serde_json, and tokio.
