## pitlane-mcp v0.10.0 — intent-aware navigation, single-call investigation, and session-aware reads

This release is the biggest architectural step since v0.9.0. It introduces a new high-level tool tier built around intent rather than implementation detail, a single-call investigation tool that replaces multi-step discovery sequences, and a session layer that tracks what the agent has already seen so it can steer toward expansion instead of redundant rereads.

### `investigate` — answer a code question in one call

The new `investigate` tool is the recommended first call after `ensure_project_ready` for any broad code question. It discovers relevant symbols using multiple search strategies, reads their source, and returns a prose answer with up to six symbol bodies inlined — all in a single round-trip.

```json
{ "project": "/your/project", "query": "How does the ignore/gitignore handling work?" }
{ "project": "/your/project", "query": "main regex search execution path", "scope": "crates/core/**" }
```

This replaces the typical `locate_code` → `read_code_unit` → `read_code_unit` → … sequence with one call, dramatically reducing conversation length and accumulated prompt tokens. For struct and class results, `investigate` automatically expands the first few methods so you see both the type shape and its key implementations.

The tool also includes session-aware deduplication: if the same query (or a rephrased equivalent) is investigated twice, it returns the cached response immediately with a `"repeated": true` flag instead of re-running discovery. A test-aware discovery phase prioritizes test files when the query mentions "test", "behavior", or "edge case".

The `pitlane investigate` CLI command is available as well, with optional `--scope` and `--lang` filters.

### New high-level navigation tools

Five new composite tools replace the need to manually choose between lower-level primitives:

- **`locate_code`** — unified entry point for ambiguous queries. Routes to symbol search, file search, or content search depending on what the query looks like, and returns steering metadata with the recommended next tool and target.
- **`read_code_unit`** — reads the smallest useful code unit once the target is known. Abstracts away the manual choice between `get_symbol`, `get_file_outline`, and `get_lines`.
- **`trace_path`** — explicit source-to-sink, config-to-effect, and shortest-path tracing with optional `source` and `sink` hints.
- **`analyze_impact`** — blast-radius analysis before edits or refactors, with ranked impacted symbols and files.
- **`navigate_code`** — umbrella tool that routes to locate, read, trace, or impact analysis when the prompt is underspecified.

These tools are now the default public tier alongside `ensure_project_ready`, `investigate`, `get_index_stats`, and `search_content`. The advanced primitive surface (`search_symbols`, `get_symbol`, `find_callers`, `find_callees`, etc.) remains available via `PITLANE_MCP_TOOL_TIER=all`.

The `pitlane` CLI gained matching commands: `pitlane trace-path` and `pitlane analyze-impact`.

### Session-aware reads and navigation

`read_code_unit` and the underlying read tools now track what has been read in the current session and report a `read_state` object on every response:

- `new` — first read of this target in the session; continue with the payload
- `unchanged` — same target, same content as the previous read; expand to usages or related symbols instead of rereading
- `changed` — same target, changed content since the previous read; use the refreshed payload before expanding

`locate_code`, `trace_path`, and `analyze_impact` may also return a `session_state` block explaining whether the top candidate was already seen, whether a nearby unseen alternative was promoted, and what the recommended follow-up is. This reduces redundant rereads and helps agents make forward progress instead of cycling over the same symbols.

Content observation uses blake3 hashing to detect changes between reads, with a bounded `MAX_RECENT_ITEMS` cache to keep memory overhead low.

### Repository archetype detection

pitlane now builds a `RepoProfile` during indexing that classifies the repository's architecture and assigns functional roles to files.

Detected archetypes include CLI, Library, Service, Frontend, Infra, Monorepo, and TestHeavy. File roles (entry point, core logic, test, config, generated, etc.) are used to boost search results based on query intent — so a query about "main execution path" naturally surfaces entry points and core files rather than test fixtures or generated code.

The profile is stored in `IndexMeta` (schema version 2) and loaded on subsequent calls without re-analysis.

### Benchmark harness

A substantial benchmark harness was built alongside this release to measure and improve pitlane's real-world impact on agent token usage and answer quality.

The harness supports multiple backends (Ollama, LM Studio, OpenCode, Bedrock), suite-based runs, resumable execution, per-instance artifacts, and a separate grading pass. Recent runs on the ripgrep prompt set show MCP using **13% fewer tokens** than a non-MCP baseline while producing **9% better quality answers** across 19 prompts. Standout results include `symbol_regex_search_path` at 0.14× (86% cheaper) and `usage_ignore_skip_path` at 0.22× (78% cheaper).

The `investigate` improvements in this release were directly driven by harness feedback, with several previously expensive prompts dropping from 1.4–13× token overhead to under 1×.

### Other changes

- Sorting logic simplified with `sort_by_key` and `Reverse` throughout.
- Test environment variable mutation tests are now isolated to prevent parallel race conditions.
- README updated with the new tool hierarchy, `investigate` documentation, and revised recommended workflow.
